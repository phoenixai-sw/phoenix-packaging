# 대표님이 준비할 항목

개발과 별개로 계정 소유자만 할 수 있는 가입·계약·도메인 인증입니다. 키를 채팅에 붙여 넣지 말고 로컬 파일로 저장한 뒤 파일 경로만 알려 주세요. 이 문서에는 실제 비밀 키를 기록하지 않습니다.

## 1. Toss Payments — 우선 테스트 키만 준비

1. [토스페이먼츠 개발자센터](https://developers.tosspayments.com/)에 가입·로그인합니다.
2. 내 개발정보 → API 키에서 **API 개별 연동 키**의 테스트 클라이언트 키와 테스트 시크릿 키를 확인합니다. 결제위젯 전용 키와 구분합니다.
3. 두 값과 선택한 상점아이디(MID)를 `C:\codex\phoenix-service-keys.local.txt` 같은 로컬 파일에 저장하고 경로를 알려 주세요. `TOSS_CLIENT_KEY=...`, `TOSS_SECRET_KEY=...`, `TOSS_MERCHANT_ID=...`처럼 적으면 됩니다. 자동결제용 상점과 키인지도 함께 확인합니다.
4. 이 단계에서는 가상 결제로 승인·중복 요청·환불·구독 흐름을 검증합니다. 실제 고객의 돈을 받는 기능은 켜지지 않습니다.
5. 실제 월 구독 서비스를 열 때 토스페이먼츠에 사업자 정보로 입점을 신청하고 **자동결제(빌링) 계약**을 요청합니다. 일반 일회성 결제 계약과 별도 확인이 필요합니다. 가입·계약에 필요한 서류와 심사 조건은 토스 안내를 따릅니다.

참고: [자동결제 연동 공식 안내](https://docs.tosspayments.com/guides/v2/billing/integration), [API 키와 상점아이디 안내](https://docs.tosspayments.com/reference/using-api/api-keys). 계약 전에는 개발 연동 체험 상점에서 제공하는 테스트 범위로 진행하며 라이브 자동결제는 별도 계약이 필요합니다. 앱의 요금안은 작업지시서의 초안이므로 실제 판매 전에 가격·부가세·환불·정기결제 고지를 확정해야 합니다.

## 2. 이메일 — Resend와 회사 도메인 준비

1. [Resend](https://resend.com/)에 가입합니다. 이미 회사 SMTP가 있으면 기존 서비스도 사용할 수 있습니다.
2. 소유한 도메인이 있으면 Resend → Domains에 등록합니다. 예: `mail.회사도메인.kr`. 도메인이 없으면 먼저 원하는 도메인을 결정·등록해야 합니다.
3. Resend 화면에 표시된 DNS 인증 레코드를 도메인 관리 업체 화면에 그대로 추가하고 인증 완료를 확인합니다. 레코드 값은 계정마다 다르므로 임의로 넣지 않습니다.
4. API 키를 만들고 위 로컬 파일에 `RESEND_API_KEY=...`, `MAIL_FROM=Phoenix Packaging <noreply@인증한도메인>`을 적습니다. 사용 중인 서비스명과 도메인도 적어 주세요.
5. 제가 서버의 SMTP 설정과 인증메일·비밀번호 재설정·팀 초대 동작을 연결합니다. 실제 메일 발송 검증은 지정한 본인 수신 주소로 진행합니다.

Resend 설정값: 서버 `smtp.resend.com`, 포트 `587`, STARTTLS 사용, 사용자명 `resend`, 비밀번호는 Resend API 키입니다. 공식 문서: [SMTP](https://resend.com/docs/send-with-smtp), [도메인 인증](https://resend.com/docs/dashboard/domains/introduction).

## 3. 제조사 — 아래 요청문 전달

현재 샘플 포장 구조는 편집·검토용입니다. 실제 주문 제작에 쓰려면 아래 자료가 필요합니다. 자료를 받으면 원본 파일을 작업 폴더의 별도 폴더에 보관하고 경로를 알려 주세요.

> 안녕하세요. 패키지 디자인 편집 및 출력 시스템을 제작 중입니다. 귀사에서 실제 접수 가능한 규격 한 가지부터 검증하려고 합니다. 아래 자료를 부탁드립니다.
>
> - 포장 종류, 도면 버전, 제조사명과 담당자
> - 승인된 실제 크기의 PDF 도면 또는 SVG/AI 원본 및 열람용 PDF
> - 완성 폭·높이, 파우치의 펼친 바닥 폭 또는 박스 깊이, 치수의 내경/외경 기준
> - 재질·두께와 가공 방식, 실링·접착·접힘 영역, 행잉홀 위치·직경·허용 범위
> - 재단선, 안전 여백, 도련, 인쇄 금지 영역과 허용 오차
> - 요구 PDF 규격, 페이지/전개도 구성, RGB 또는 CMYK/ICC 프로파일, 별색·백색·오버프린트 여부
> - 글꼴 임베딩 또는 아웃라인 조건, 최소 글자 크기·선 굵기·이미지 해상도
> - 바코드 형식·최소 크기·검증 기준 및 실제 코드의 소유권 확인 방식
> - 도면의 서비스 내 사용·배포 허용 범위, 출처 및 라이선스
> - 샘플 출력 파일 접수 후 승인/반려 사유를 회신해 주실 수 있는지
>
> 제공하신 조건과 시스템이 지원하는 출력 형식이 일치하는 경우에만 제작용 출력을 허용하겠습니다.

현재 제작 출력 엔진은 실제 크기의 면별 PDF, RGB, 임베드한 글꼴을 지원합니다. PDF/X·CMYK 변환·별색·백색판·오버프린트·글꼴 아웃라인·복잡한 제조 전개도를 지원한다고 가정하지 않습니다. 제조사 요구가 이 범위를 넘으면 해당 기능을 추가 구현·검증한 뒤 활성화해야 합니다.

## 준비 순서

오늘은 **Toss 테스트 키 → 이메일 서비스 및 도메인 → 제조사 규격 한 가지** 순서로 준비하면 됩니다. 모두 한 번에 준비할 필요는 없습니다. 자료가 없는 동안에도 편집, 구조 미리보기, AI 생성, 검토용 PDF와 모의 결제 검증은 계속 개발할 수 있습니다.

개발 완료와 상용 운영 승인은 구분됩니다. 결제 계약, 실제 이메일 발송, 제조사 접수 승인, 가격·환불·개인정보 정책은 증빙 없이 완료 처리하지 않습니다.
