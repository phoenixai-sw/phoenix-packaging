# 보관·지원·삭제 운영

원문 §12.5·§17의 보관 상태, 만료 예고, 소유자 삭제 요청, 분쟁 보존과 사유 있는 운영 지원 접근을 구현한다. 이 문서는 코드 기능을 설명하며 운영 자료 삭제나 새로운 보관 약관 확정을 의미하지 않는다.

## 보관과 안내

`/app/retention`은 소유자 전용이다. 마지막 유료 기간 종료+90일과 구매 크레딧 만료 중 늦은 기한을 영속 저장하고 이미 계산된 기한을 줄이지 않는다. trial만 있는 조직에는 임의 삭제 기한을 만들지 않는다. 기준일 30·7·1일 전/경과 알림을 앱 안에 중복 없이 남긴다. 구독이 연장되면 이전 기한 알림은 대체 상태가 된다. 이메일 발송은 연결하지 않았다.

기한 경과만으로 고객 파일을 삭제하거나 소유자의 기존 다운로드를 막지 않는다. 프로젝트·리비전·장면·완료 파일은 별도 요청 없이 유지된다. 팀원의 유료 기간 종료 접근 차단은 기존 구독 권한 정책을 따른다.

## 삭제 요청과 실행 범위

소유자가 대상과 사유를 접수하면 해당 자료에 요청별 보존 hold를 추가한다. 같은 요청 키와 본문은 같은 결과를 돌려주며, 다른 본문 재사용은 거절한다. 관리자는 사유와 버전 번호를 확인하여 승인 또는 반려한다. 승인 즉시 파일을 지우지 않는다.

실행 가능한 범위는 **참조되지 않는 개별 이미지 파일(asset)**과 **완료된 출력 파일(export)**이다. 파일 크기·SHA-256·실제 소유 저장 키를 서버에서 검증하여 승인 시 동결하고 최소 7일 유예한다. 소유자는 실행 시작 전 취소할 수 있다. 유예기간이 지나도 보존 상태가 있으면 계속 유지한다. 조직·프로젝트 전체 삭제는 요청과 검토만 지원한다. 장면·저장본·여러 프로젝트의 공유 자료·법정/분쟁 관련 원장을 함께 제거하는 기능은 구현하지 않았다.

실행 직전 다음을 검사한다.

- 조직/해당 프로젝트/파일의 분쟁·수동·지원 hold. 요청 자신의 hold만 실행 단계에서 제외한다.
- 진행·대기·결과 불확실 작업, 업로드, 진행/실패 백업의 보호 상태.
- 현재 장면과 모든 저장본, 작업 snapshot/result, AI 결과, 브랜드 로고, 파생 원본 계보, 유효한 견적, 제조사 입고 기록, 승인 증빙의 참조.
- 승인한 객체의 경로·크기·해시 동일성. 검사가 불확실하거나 참조 검색 상한을 넘으면 삭제하지 않는다.

접근 종료 tombstone을 먼저 DB에 확정하고 별도 트랜잭션에서 파일을 삭제한다. 삭제 응답이 끊기면 원본을 다시 읽거나 저장소의 명시적 부재를 확인하여 재처리한다. 원본을 조용히 다시 생성하지 않으며, 소유자 요청 삭제를 AI 소실 사고로 보상하지 않는다. 완료한 파일은 목록에서 제외되고 다운로드·새 장면 연결은 410이다. 결제·크레딧·작업 이력과 장면/저장본은 수정하지 않는다. 삭제된 원본은 DB tombstone으로 남고 기존 암호화 백업 사본을 역으로 수정하지 않는다.

`RETENTION_CUSTOMER_DELETE_ENABLED=false`가 기본값이다. true여도 승인된 단일 파일 요청만 처리하며, hosted는 `OPERATING_POLICY_APPROVED=true`가 추가로 필요하다. 웹 UI에는 이 실행 상태를 표시한다. 운영 QA에서는 이 플래그를 켜거나 고객 자료를 삭제하지 않았다. 실행·예외 복구는 격리된 로컬 fixture만 사용했다.

## 지원 접근

`/admin/operations`에서 플랫폼 관리자만 tenant와 정확한 대상, 5–1,000자 사유를 기록하여 30분 읽기 권한을 만들 수 있다. 권한은 발급한 사용자와 해당 로그인 세션에 묶이며 다른 세션, 철회, 만료는 거절한다. project 범위는 그 프로젝트의 현재/이전 장면에 실제 연결된 이미지와 출력만 포함한다. 임의 UUID로 범위를 넓힐 수 없다.

자료를 돌려주거나 서명 URL을 만들기 전에 열람 대상·사유·시각·담당자를 감사 기록에 확정한다. 일반 관리자 계정의 기존 고객 API 권한을 우회하지 않고 별도 지원 경로만 사용한다. private URL TTL은 60초와 남은 지원 시간 중 짧은 값이다. 소유자는 자기 조직 지원 접근 기록을 볼 수 있다. 편집·삭제·사용자 세션 대행은 지원하지 않는다.

## 백업과 미게시 파일 정리

암호화 백업 스크립트는 고객 데이터를 한 읽기 전용 snapshot에서 읽는다. 별도 control 트랜잭션으로 시작/보호/검증 상태만 기록한다. 백업 시작은 삭제와 공통 gate를 잡고, 복사 대상 pin과 검증 manifest 해시를 남긴다. 실패·프로세스 중단 보호는 시간만으로 풀지 않는다. 오류 상태는 운영자의 사유로 종료하며, 24시간 이상 응답 없는 실행 상태는 프로세스가 실제 종료됐다는 명시적 확인도 요구한다. 실행 중인 프로세스를 이 버튼이 종료하지는 않는다.

`STORAGE_GC_DELETE_ENABLED=false`가 기본이다. GC는 버킷 목록을 탐색하지 않고 서버 worker가 쓰기 전에 등록한 immutable write intent만 살핀다. review/production/editable ZIP과 AI worker의 lease별 경로에 적용한다. 24시간 이상 지난 미게시 파일을 최소 5분 간격으로 두 번 관찰하고, 참조·진행 작업·hold·백업·크기·해시를 재검사한다. 알 수 없는 파일, 기존 업로드 원본, 게시된 파일은 이 GC가 삭제하지 않는다. 객체가 다르거나 저장소가 불확실하면 보존한다. 기존 만료 업로드 quarantine 정리는 별도 경로지만 같은 hold와 백업 barrier를 확인한다.

이미지 업로드/화질 보완 중 DB 저장 전에 실패한 미등록 파일까지 bucket-scan으로 추정 삭제하지 않는다. 이런 unknown 파일은 이번 자동 정리 범위 밖이며 저장소 운영 조사가 필요하다.

## API와 적용

신규 JSON 응답은 `Envelope[T]`, 오류는 공통 오류 schema이다. 파일 응답은 binary/307이다. 소유자 API는 `/retention`, `/notices`, `/retention/access-history`, `/deletion-requests`와 detail/cancel. 관리자 API는 `/admin/retention/overview`, holds/create/release, deletion review/retry, support session create/revoke/read, backup abandon이다. 쓰기는 CSRF와 실제 역할을 검사한다. 상태 변경은 revision CAS와 tenant/write gate를 사용한다.

`0011_retention_support` → `0012_storage_lifecycle` → `0013_service_orders` → `0014_customer_deletion` 순서다. 0014 이전에 승인된 요청에는 due/snapshot이 없으므로 자동 실행에 들어가지 않는다. 적용 전에 검증된 설정과 암호화 백업을 준비하고, worker를 잠시 중단한 상태에서 Alembic을 적용한 다음 API/worker를 올린다. 삭제 플래그는 OFF로 유지한다. downgrade 전에 실행 중 요청과 보존/백업 control 자료를 별도로 보존해야 한다. control schema 제거는 파일 복원 수단이 아니다.

검증 근거는 `test_retention_ops.py`, `test_retention_execution.py`, `test_retention_migrations.py`와 기존 `test_backup_restore.py`, `test_editable_exports.py`, `test_uploads.py`이다. 별도 프로세스/SQL 연결에서 GC와 백업의 동시 시작, 물리 삭제 직후 프로세스 종료로 DB commit이 유실된 경우도 검증한다. 실제 PostgreSQL 경합·hosted 저장소 삭제와 새 화면 운영 브라우저 검증은 이 작업의 로컬 테스트와 구분해야 한다.
