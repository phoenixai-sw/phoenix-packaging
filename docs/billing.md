# 크레딧·구독·결제 구현

P2의 크레딧 원장과 결제 상태 처리는 실제 SQL 트랜잭션으로 구현했다. 기본 정책은 `config/pricing.seed.json`의 제안 버전이며 라이브 결제는 비활성이다. 모의 PG 테스트와 실제 Toss 상점에서 수행한 테스트는 구분한다. 현재 실제 Toss 테스트·라이브 키를 사용한 승인 검증은 미실시다.

## 크레딧 계약

- 가입 조직당 체험 지급 키는 고정되어 30크레딧을 중복 지급하지 않는다. 만료는 최초 가입 시각부터 14일이고 표준 이미지 생성·수정에만 사용한다. 자동 유료 전환은 없다.
- 월·구매·체험·오류 복원 버킷을 구분하고, 만료가 빠른 버킷부터 예약한다. 같은 만료일이면 지급 시각과 ID 순서다. 조회·예약 모두 현재 유효기간을 확인하므로 만료 배치가 늦어도 사용할 수 없다.
- 작업별 비용은 서버 정책에서 읽는다. 표준 생성·수정 10, 고해상도 생성 20, 최초 제작 묶음 40, 같은 제작 항목의 재출력·검토 출력 0이다. 고해상도 수정은 지원하지 않고 생성도 `AI_HIGH_ENABLED=true` 전까지 차단한다.
- `create_quote`는 5분짜리 견적에 리비전, 정규화 입력·해시, 정책 버전, 수량과 비용을 고정한다. 공개 API는 루트의 `prepare_quote`에서 상품·구조·자산 권한을 검증하고 서버 기준 입력을 만든다. 제작 검수 훅이 없으면 제작 견적을 차단한다.
- `reserve`는 조직 지갑을 잠그고 버킷을 예약한다. 조직·작업 키의 고유 제약과 요청 해시가 중복·변조를 막는다. `capture_unit`과 `release_unit`은 0부터 시작하는 결과 번호별로 정산한다. 3장 중 2장 성공은 30예약·20확정·10반환이다.
- 40분 예약 상한이 지난 결과는 새로 차감하지 않는다. 만료된 원 버킷으로 돌려줄 수 없는 실패분은 기존 이용 범위를 그대로 가진 보상 버킷으로 복원하고 7일을 보장한다. 체험 복원이 제작 권한으로 바뀌지 않는다.
- 원장은 GRANT·RESERVE·CAPTURE·RELEASE·EXPIRE·COMPENSATE·ADJUSTMENT의 불변 행이다. ORM 검사와 PostgreSQL/SQLite 트리거가 수정·삭제를 차단한다. 환불은 원 결제를 보존한 채 반대 전표를 기록한다. 잔액 UI는 환불 정정분과 자연 만료분을 구분한다.

`services.api.billing.service` 함수는 **커밋하지 않는다**. 작업 결과 공개와 `capture_unit`을 같은 트랜잭션으로 커밋해야 한다. 실패·DB 롤백 시에는 제공하지 못한 결과를 청구하지 않는다. 객체 저장 성공만으로 CAPTURE하지 않으며, 결과 파일을 확인하는 책임은 작업 실행 계층에 있다. 저장 후 접근 불가가 확인된 결과에는 `compensate_unit`을 멱등 호출한다.

완료된 AI 이미지는 `reconcile_ai_assets`가 매 worker 실행에서 기본2개씩 오래된 검사 순서로 확인한다. 최초 검사는 완료5분 후 가능하며 정상 파일은24시간 뒤 다시 확인한다. 소실 또는 동일 체크섬 손상을5분 이상 간격으로 두 번 확인해야 원 이용 범위·최소7일 보상 크레딧을 한 번 지급한다. 타임아웃·권한·버킷·불명확한 응답은 확정 증거를 초기화하고 보상하지 않는다. Supabase 객체 부재는 다운로드 오류 외에도 권한이 있는 서버 키, 정상 버킷 조회, 별도 객체 목록의 부재가 필요하다. 보상·자산 사용 불가 상태·작업 결과·감사 기록을 한 트랜잭션으로 확정하고 해당 파일 다운로드와 참조 수정은410으로 안내한다. 자동 재생성·재차감은 없다. 이 감시는 완료된 AI 이미지 대상이며 모든 제작 ZIP의 사후 무결성 감시를 의미하지 않는다.

## 제작 항목

제작 지문은 조직·브랜드·안정된 상품 변형 ID·정규화 내용량·바코드·구조 과금군·완성 치수·구멍 가공으로 계산한다. 500g와 0.5kg는 같다. 상품명 오타, 레이아웃, 인쇄 수량, 프로파일·재질명만의 변경은 같은 항목이다. 물리 치수·바코드·가공이 바뀌면 새 항목이다.

동일 지문의 동시 최초 제작은 하나만 예약할 수 있고, 완성 묶음이 검증된 결과를 확정할 때만 제작 권한을 만든다. 실패한 묶음에는 권한을 주지 않는다. 무료 재출력도 제조사·프로파일·리비전 검수를 생략하지 않는다. 현재 지문 정책은 `physical-identity-v1`로 기록하며 향후 정책 변경 때 기존 권한을 소급 변경하지 않는 별도 마이그레이션이 필요하다.

## 결제·갱신

주문 가격·VAT 포함 결제액·지급량은 서버 정책으로 만든다. 클라이언트 금액, 카드 등록 성공, success URL 방문 또는 웹훅 본문만으로 결제 성공 처리하지 않는다. PG의 주문 ID·금액·통화·MID·paymentKey·DONE 상태를 검증하고 지급·청구 상태·알림 outbox를 함께 커밋한다.

Toss 일반 결제는 `/v1/payments/confirm`, 자동결제는 billingKey 발급 후 `/v1/billing/{billingKey}`를 사용한다. customerKey는 무작위로 만들고 billingKey와 함께 Fernet으로 암호화해 보관한다. 카드 번호·CVC를 받거나 저장하지 않는다. 응답 유실은 같은 orderId로 재조회하며 확정되지 않은 결과는 `reconciliation_required`로 남긴다.

일반 결제 웹훅에 공통 서명 헤더가 있다고 가정하지 않는다. 알림은 기존 주문을 찾는 용도로만 사용하고 PG 조회 응답으로 처리한다. 검증한 결제 상태의 이벤트 키를 중복 방지에 사용하므로 위조·중복·순서 역전 본문이 잔액을 바꾸지 못한다. HTTP 클라이언트 로그에도 billingKey가 포함된 Toss URL을 남기지 않는다.

구독은 Asia/Seoul의 원래 가입일과 UTC 주기 시각을 보관한다. 31일 → 짧은 달 말일 → 다음 31일을 유지한다. `(subscription_id, period_start)`가 고유한 청구서의 orderId로만 갱신한다. 실패한 주기에 새 크레딧을 주지 않으며 같은 청구서를 최대 3번, 최초·24시간·72시간 시점에 시도한다. 끝난 과거 주기를 뒤늦게 자동 청구하지 않는다.

갱신 청구서·주문은 PG 호출 전에 별도 트랜잭션으로 먼저 커밋한다. PG 승인 직후 worker가 종료되어도 같은 주문을 조회하므로 이중 청구하지 않는다. 재시도가 끝났거나 아직 대기 중인 청구서는 다른 조직의 갱신 조회 한도를 차지하지 않는다. 최초 빌링 승인 중 프로세스가 종료된 경우도 일회용 인증 키 재사용 전에 기존 주문을 조회한다. 승인만 복구되고 결제 수단 키는 저장되지 않았다면 자동 갱신을 중단한 구독으로 복구한다.

상향은 남은 초/전체 주기 초에 따라 금액 차이를 원 단위 반올림하고 크레딧 차이는 내림한다. 5분 견적을 결제 전에 보여 주며 원 요금제와 주기가 바뀌면 재견적을 요구한다. 하향은 다음 갱신부터 적용한다. 해지는 현재 기간을 유지하며 다음 갱신을 막는다. 기간 종료 시 소유자 1좌석과 유효 구매분을 유지하고 다른 팀원의 접근을 차단한다. 파일 보관 기한은 마지막 유료 기간 종료+90일과 구매분 만료 중 늦은 시각이다. 실제 삭제 작업은 자동으로 실행하지 않는다.

환불 자동 처리는 **전혀 사용·예약·만료하지 않은 주문의 전액 취소**만 지원한다. 사용 내역이 있는 주문과 부분 환불은 검토 상태로 안내하며 소비 내역을 삭제하거나 음수 잔액으로 숨기지 않는다. PG에서 직접 발생한 취소는 조정 검토 outbox를 남긴다. 운영 환불 약관이 확정되지 않아 라이브 게이트는 닫혀 있다.

## 환경과 실행

- `PAYMENT_PROVIDER=disabled|mock|toss_test|toss_live`
- `BILLING_ENCRYPTION_KEY`: Fernet 키. 소스나 브라우저에 포함하지 않는다.
- Toss: `TOSS_SECRET_KEY`, `TOSS_CLIENT_KEY`, `TOSS_MERCHANT_ID`
- 라이브는 키뿐 아니라 `BILLING_POLICY_APPROVED=true`, `LIVE_BILLING_ENABLED=true`, 버전 정책의 `live_billing_enabled=true`가 모두 필요하다.
- 라이브는 `APP_ENV=production`에서만 허용하며 Toss 테스트는 production에서 차단한다. 테스트·라이브 상점 키를 환경 간 바꾸어 사용하지 않는다.
- `mock`는 development/test에서만 허용하며 staging/production에서는 모의 승인 경로를 노출하지 않는다. 공개 호스팅에서 임의 크레딧을 지급하는 API는 없다.

주기 worker는 `process_due_invoices(session_factory, provider=..., settings=...)`와 `reconcile_pending_orders(...)`를 호출한다. 후자는 확인이 지연된 주문을 재조회할 뿐 새 결제를 만들지 않는다. `deliver_outbox`는 예약과 연결된 영구 SQL 작업이 존재할 때만 큐 인계를 확인하고, 결제 알림은 내부 감사 기록에 남긴다. 소비 기록과 확인 시각은 한 트랜잭션으로 커밋하며 중복 worker도 한 번만 반영한다. 외부 이메일 발송 기능은 이 소비자에 포함하지 않는다. PG 미연결 상태에서는 결제 처리기를 호출하지 않는다. 일부 작업 분배가 실패하면 다른 큐는 계속 처리하며 보호된 worker API는 내부 오류 내용을 노출하지 않는 재시도 가능 HTTP503을 반환한다.

```powershell
.\.venv\Scripts\python.exe -m pytest services/api/billing/tests -q
```

검증에는 부분 성공, 30잔액에 20요청 동시 2개, 중복 결과, 만료·7일 복원, 출력 지문·권한, DB 롤백, 암호화, 위조·중복 웹훅, 승인 응답 유실, 월말·윤년, 구매분 보존, 상향·하향·해지·좌석, 중복 스케줄러, 환불 이력, 호스팅 모의 결제 차단, 실제 마이그레이션의 원장 수정·삭제 차단을 포함한다. 이는 실제 Toss 상점 승인이나 PG 계약 완료의 증빙을 대신하지 않는다.
