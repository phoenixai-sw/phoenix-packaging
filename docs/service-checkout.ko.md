# 수락 견적의 서비스 수납과 첫 달 Pro

이 기능은 원문 §12.1 별도 주문 항목과 §16 `/v1/billing/orders` 일회성 주문을 연결한다. 코드 구현으로 운영 PG·라이브 결제·환불 정책을 활성화하지 않는다. 기존 Toss 계정/키/MID, 정책 승인, 서버 live 플래그, 게시된 요금 정책의 모든 게이트가 그대로 필요하다. 테스트는 격리 DB와 MockProvider로만 수행한다.

## 가격과 수락

- `file_review`: VAT 포함 55,000원 제안. 상품당 파일 검토 1회와 보완 확인 1회.
- `onboarding`: VAT 포함 100,000원 제안. 일회 사용 안내. 자동 갱신·크레딧·제작 출력 자격 지급 없음.
- 일반 일회 서비스의 최종 금액·범위·제외 항목은 관리자가 낸 견적을 소유자가 수락한 값이다. 브라우저는 결제 금액을 정하지 못한다.
- `pilot_pro_first_month`: VAT 포함 첫 달 99,000원 제안. 현재 Pro 정상 월 요금은 VAT 포함 108,900원, 월 1,500크레딧·3좌석이다. 정상 월 요금과 제공량은 견적 작성 당시 서버 요금표에 고정된다. 실제 운영 정책을 확정했다는 의미가 아니다.
- 첫 달 할인은 현재 기준 9,900원이다. 첫 달 중 상향할 때 남은 기간 차액은 실제 첫 달 결제액 99,000원을 기준으로 계산한다. 다음 정상 갱신 요금표를 할인 가격으로 덮어쓰지 않는다. 상향은 기존 별도 서버 견적과 결제 확인을 거친다.
- 수락은 결제가 아니다. 첫 달 Pro 결제 주문에는 소유자가 첫 금액·이후 금액·자동 갱신·Pro 요금제·조건 버전을 명시적으로 확인한 `recurring_consent`가 추가로 필요하다.
- 과거 문의/견적/수락본의 `checkout_terms`는 NULL로 남긴다. 구견적에 자동 결제 권한을 소급 부여하지 않는다. 관리자의 새 견적 발행과 소유자 재수락이 필요하다. 이전 견적은 유지된다.

## API

기존 `POST /v1/billing/orders`, `Idempotency-Key`를 사용한다.

```json
{
  "kind": "service",
  "service_order_id": "신청 UUID",
  "service_quote_id": "수락 견적 UUID",
  "service_base_revision": 3,
  "recurring_consent": {
    "terms_version": "서버가 반환한 64자리 조건 해시",
    "first_amount_inc_vat": 99000,
    "renewal_amount_inc_vat": 108900,
    "currency": "KRW",
    "automatic_renewal": true,
    "plan_id": "pro"
  }
}
```

일회 서비스에서는 `recurring_consent`를 생략한다. `amount`, `credits`, `plan_id` 직접 주입은 거부한다. 일반 서비스 응답은 `kind=service`, `checkout_kind=payment`; 첫 달 Pro는 `kind=subscription`, `checkout_kind=billing_auth`이다. 기존 승인·빌링키 등록·모의 승인·상태 조회·환불 엔드포인트를 재사용한다. 주문 응답에는 신청·견적 ID, 코드, 이름이 추가된다.

서비스 DTO는 업무 `status`와 별개로 `payment_status`, `payment_order`, `checkout_terms`, `checkout_enabled`, 차단 이유, 같은 주문의 재시도 가능 여부, 환불 가능 여부, 연결 구독 상태를 제공한다. 구독 DTO의 기간은 한국 시간의 가입일 기준 월 갱신 로직을 그대로 사용한다.

## 정합성·재시도·환불

- 조직 지갑 잠금 안에서 소유자·조직·신청 버전·수락 견적·유효 기한을 확인한다. 신청별 결제 연결은 DB unique로 하나만 만든다. 동일 키/동일 입력은 기존 주문을 돌려주고, 입력 변경 또는 새 키 중복 주문은 409다.
- PG 응답 유실 후에는 기존 주문을 재조회한다. `reconciliation_required` 서비스 주문은 추가 승인을 시작하지 않는다. `pending`/`failed`는 생성 30분 안에서 같은 주문만 재시도한다. 만료된 주문의 새 승인도 차단하지만 이미 성공한 결제의 재조회·동기화는 계속 허용한다.
- 일반 일회 수납은 크레딧 원장 지급, 청구서, 구독, `ever_paid` 제작 자격을 만들지 않는다. 환불과 재조회도 크레딧 원장을 조작하지 않는다.
- 새 유료 견적 업무는 수납 확인 뒤 진행한다. 과거 결제 조건 없는 일반 업무와 0원 견적은 기존 수동 업무 처리를 유지한다. 결제와 업무 상태를 자동으로 같은 값으로 바꾸지 않는다.
- 일회 서비스 자동 전액 환불은 업무 시작 전만 가능하다. 업무 시작과 환불은 같은 조직 잠금으로 직렬화한다. 외부 PG에서 확인된 부분 환불은 정산 검토 상태로, 전액 취소는 실제 환불 상태로 기록하되 업무 이력을 지우지 않는다.
- 첫 달 Pro는 기존 구독 등록 이력이 없는 조직만 가능하다. 수납 확인 후 정확히 한 번 1,500크레딧과 Pro 기간/좌석을 적용한다. 다음 달은 고정된 정상 요금으로 기존 갱신 청구를 사용한다. 해지하면 현재 기간은 유지하고 다음 신규 청구를 만들지 않는다.
- Pro 환불은 기존 미사용·미예약·미만료 크레딧 조건을 적용한다. 관리자가 신청 업무를 완료했더라도 이 조건을 충족하면 구독 환불 검토가 가능하다. 사용분이 있으면 잔액을 임의 삭제하지 않는다.
- 서명처럼 보이는 웹훅 본문을 신뢰하지 않는다. 기존 서버 재조회, 주문·금액·통화·MID·결제키 검증과 append-only Payment/PaymentEvent 원장을 재사용한다.

## 마이그레이션·운영 한계

`0018_service_checkout`의 부모는 `0017_metrics`다. 기존 견적에 nullable JSON 한 열을 추가하고, `service_checkouts`에 수락 견적/지급 주문/소유자/조건/동의 증거를 저장한다. 신규 테이블은 RLS와 PUBLIC/anon/authenticated 접근 차단을 적용한다. 견적과 checkout 증거의 UPDATE/DELETE를 DB trigger로 차단한다. 기존 견적·주문·정산값의 backfill이나 가격 변경은 없다.

운영 적용은 기존 암호화 백업·격리 앱 복원 확인 뒤 API 배포와 마이그레이션 순서를 조율한다. 새 코드는 0018 열/테이블을 요구한다. 이전 코드는 새 nullable 열을 무시할 수 있다. 결제 연결 행을 생성한 뒤에는 운영 downgrade로 이력을 버리지 않는다.

실제 Toss 테스트 상점 승인/빌링키/갱신/취소/웹훅 실검증과 실제 사람의 서비스 제공은 별도다. 전문가 자동 배정은 후속 기능이다. 결제 결과가 불명확하거나 부분 환불·업무 제공 후 취소인 경우 기존 정산 검토를 거치며 성공으로 표시하지 않는다.

공식 근거: root가 설정된 Toss MCP로 조회한 [자동결제 연결](https://docs.tosspayments.com/guides/v2/billing), [API 문서](https://docs.tosspayments.com/reference). MCP 원문은 비공개 로컬 QA 자료로 유지한다. 새 결제 어댑터나 새 키는 추가하지 않았다.
